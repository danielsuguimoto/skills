name: pr-test
description: "Test or verify a PR through real entry points, with the user or agent driving. Supports `quick` and `budget <N>`."
---

### 0. Confirm the Test Driver

Before loading PR context, checking out a branch, or preparing runtime/data, ask: **Who will drive the test actions?** Use the interactive question tool where available, with these choices:

- **User** — the user performs test actions; the agent guides and verifies them.
- **Agent** — the agent performs the test actions through real entry points and verifies effects; ask for human-only access or actions when needed.

Record the answer as `<test-driver>` = `user` or `agent`. An unanswered or skipped choice pauses the workflow; there is no default driver. Keep the choice for the session and change it only on the user's request. For `user`, read and follow [user-driven testing](user-driven.md); both drivers use the same scope, plan, preparation, and proof rules below.

## Required `<project-root>/docs` reads

Shell-read before testing the PR; may be gitignored — missing → note gap, never invent: `<project-root>/docs/git-hosts.md`; `<project-root>/docs/issue-trackers.md` for linked requirements · `<project-root>/docs/database-tools.md` when provisioning or verifying data · `<project-root>/docs/code-navigation.md` only when locating an in-scope entry point or diagnosing a concrete failure · `<project-root>/docs/browser-automation.md` for agent-driven UI execution.

Act as a human QA engineer. Spend most effort proving `<pr-purpose>` through realistic use. Test the main journeys and clear, critical edge cases; touched files and methods are not a coverage checklist. Stop when the scoped behavior has evidence, not when every nearby code path has been exercised.

**Boundary:** invoking this skill authorizes its in-scope, non-destructive local setup and testing under the selected driver, including starting processes, applying non-destructive migrations and seeders, and creating fixture data. Have the selected driver execute PR-shipped migrations, seeders, operations, and scripts, added or modified, without separate execution permission, including their intended reversible changes to existing local data. Follow project safety and approval rules. Verify the database target is local from configuration and connection details before migrations, seeders, operations, or fixture writes; if uncertain, stop and ask. Inspect their effects first. Describe and obtain explicit approval for each irreversible destructive action or real-world side effect, including those in PR-shipped artifacts, and before overwriting or deleting existing local data outside their intended reversible changes, except prior report and evidence files for this PR. Replace those files without asking permission or archiving them; this overrides the replacement-approval requirement in [reporting.md](reporting.md), while its storage safety checks still apply. Keep production read-only and leave the PR thread, application source/tests, and repository history untouched. Local file writes are limited to the ignored QA report package and an explicitly approved narrow repository-local exclusion under reporting.md. Testing runs against the existing local database, destructive artifacts included.

**Completion gate:** every planned scenario has a result. `PASSED` means execution met its assertions; `FAILED` means it contradicted an assertion; `BLOCKED` means a prerequisite could not be prepared or a required action was unavailable/declined under Step 6, with the missing prerequisite, each applicable preparation path attempted, unreachable, or absent, and unblock path recorded; `DEFERRED` means requested depth, scenario budget, or the user ending the session excluded it, with a reason. Missing evidence never means `PASSED` or `FAILED`.

### 1. Interpret Arguments

PR number/URL → `<pr-ref>`; `quick` → `<test-depth>` = `quick` (default `full`); `budget <N>` → `<scenario-budget>` = `<N>` (default uncapped); focus areas or constraints → `<additional-context>`. No PR reference → derive from conversation or the current branch's open PR (`git-hosts.md`).

### 2. Load PR Context

Read the PR and diff (`git-hosts.md`). Extract `<pr-purpose>`, `<pr-branch>`, `<base-branch>`, `<pr-number>`, `<pr-url>`, and the tickets that define its requirements as `<ticket-refs>`. Distinguish those tickets from historical or incidental references. Unloadable PR → STOP.

Load reviewer feedback through `git-hosts.md`: review threads with resolution state, non-empty review bodies, and flat comments, automated reviewers included. Extract `<review-findings>` — each concrete claim, question, or claimed fix about observable in-scope behavior — with source link and state; a finding about code or behavior the current head no longer carries is `<premise-drift>`. Style, naming, and process remarks are not findings. Unloadable feedback → record the gap and continue.

Identify `<data-artifacts>` — shipped migrations, seeders, operations, and scripts — and any clear, critical risk directly caused by the change. Read code only to locate execution entry points, understand a reproduction-critical condition, or diagnose a concrete failure. Shared code changes alone do not require caller inventories or an application-wide pass.

### 3. Load Linked Context

Load each `<ticket-refs>` entry's body and checklists (`issue-trackers.md`), reusing in-session copies that cover both. Read comments, attachments, or nested links only to resolve a missing requirement or reproduction detail; this scope also governs generic tracker loading instructions. Tool failure → try a configured alternative. If user access or missing content is necessary, ask once; unavailable → record the gap and continue with supported requirements.

Extract `<expected-outcomes>` as the observable behavior the PR promises. Implementation steps, helper methods, test-writing tasks, and validation commands are not separate user journeys; use them to locate behavior or existing checks. Record `<client-cases>` when the source contains a customer report, keeping the reported steps and data conditions that matter to the failure. Historical context does not expand the PR's purpose.

Build a compact `<coverage-map>` from these outcomes to assertions in the planned journeys or focused checks. Flag missing implementation. An outcome whose premise no longer exists → `<premise-drift>`; explain it in the report rather than inventing a scenario for it.

**Done when:** every defining ticket is loaded or has a recorded gap; every observable promised outcome, reported customer case, and behavioral review finding from loaded sources is recorded; shipped artifacts and identified critical risks are listed; the coverage map records any missing implementation and premise drift.

### 4. Align Local Branch

Record `<previous-branch>`. Uncommitted changes → STOP, ask the user to stash/commit. Fetch the PR head and record its commit → `<pr-head-commit>`. Check out `<pr-branch>` — `git switch <pr-branch>` when the local branch exists (checkout tools fast-forward only and fail on a diverged branch); else through project tooling (`git-hosts.md`); failure → STOP. Behind `<pr-head-commit>` → sync it yourself per `git-hosts.md`: fast-forward to `<pr-head-commit>` — behind alone never blocks. Ahead or diverged → `git checkout --detach <pr-head-commit>` — the branch ref and its local commits stay untouched; testing never aligns by pushing or rewriting them. Verify HEAD == `<pr-head-commit>` before proceeding — evidence against a stale head is invalid. Restore `<previous-branch>` when testing ends.

### 5. Build the Test Plan

Read [reporting.md](reporting.md) and check destination safety before inspecting any previous report. Reuse useful scenarios that fit the current PR, depth, and budget; check the PR for new scenarios. Rerun selected scenarios and collect fresh evidence; previous results do not prove the current run.

Write a small `<test-plan>` around natural user journeys. A journey may span pages, actors, and lifecycle steps. Each selected journey runs the flow containing the change end to end — entry, the changed point, and the steps after it. Where the change guards one path through that flow (validation, gate, constraint), selected journeys exercise both branches: the pass-through that still completes the flow, and the guarded outcome, which ends at the rejection with its blocked downstream effects verified absent. Admit a new scenario only when it proves a distinct in-scope behavior or critical risk that selected execution evidence does not already prove. Put related assertions into the same journey; scenario labels do not require separate executions.

- **Purpose** — exercise the PR's promised behavior, including the reported customer failure where applicable. Reuse that execution for the requirements it proves.
- **Data-artifact** — in `full`, execute every `<data-artifacts>` entry against representative populated local data and verify its schema/row effects. Fold this into a purpose scenario when the same execution proves both; otherwise add a dedicated artifact scenario. Re-run only where idempotency is claimed.
- **Critical edge** — add only an explicit requirement or an obvious, high-impact failure tied to the purpose or a changed security/data-integrity boundary. State the concrete risk. Use representative cases, not permutations of roles, tenants, dates, flags, and legacy states. Keep detailed input matrices in existing focused tests.
- **Reviewer finding** — admit a `<review-findings>` entry that claims, questions, or claims to fix a distinct in-scope behavior a selected execution does not already prove. Verify the claim against the tested head; a confirmed defect fails like any other. Fold the check into the journey sharing its entry point rather than adding a standalone scenario. Findings without observable behavior need no scenario.

`quick` selects the main-purpose journeys, including the reported failure, and defers standalone artifact, reviewer-finding, and optional edge checks. Run and verify artifacts that are prerequisites for those journeys, recording them within the journey rather than deferring required setup. A failed `quick` scenario stays `FAILED`; expand depth only when the user requests it.

Prioritize the purpose, then clear critical risks and admitted reviewer findings. Select complete dependency chains before applying `<scenario-budget>`: prerequisites run before dependent assertions and count within a journey when they are part of the same scenario. If a required chain cannot fit, defer it and select a smaller complete journey rather than a check whose prerequisite was cut. Apply depth and budget before detailed setup or data provisioning.

Give each scenario an ID, source outcome, entry point, prerequisites, observable assertions, and a `parallel-eligible` flag; add the risk for an edge or reviewer-finding scenario. Decide parallelism here rather than after data preparation: where `<test-driver>` = `agent` and candidate scenarios can satisfy Step 7's parallel conditions, plan them for independence — dedicated actors, tenants, and records — and mark them parallel-eligible. Assign reporting.md's scenario/assertion IDs and intended proof checkpoints without adding scenarios. Deferred IDs need only their source and reason. Out-of-scope permutations need no scenario rows; summarize that boundary once. Every non-drifted promised outcome and each behavioral `<review-findings>` entry maps to a selected assertion or a deferred ID; findings without observable behavior need no rows, and implementation and automated-test checklists do not inflate this ledger.

**Done when:** the plan accounts for the purpose, required artifacts, and clear critical risks through selected or explicitly deferred work; each selected journey runs its changed flow to completion — both branches where the change guards one — with executable dependency chains; and no scenario repeats evidence another selected execution already supplies. Initialize its in-progress report under reporting.md before Step 6; unresolved storage safety pauses testing.

### 6. Prepare Minimal Local Data

Prepare the shared baseline first, then the main journey's data, and later prerequisites when needed. Start only the required local processes and bring the local database to a working baseline — apply the project's migrations and seeders where it ships them, except selected `<data-artifacts>`; prepare their pre-state, then execute them under the selected driver through Step 7's pre-state/execution/post-state procedure before preparing any dependent journey. Dedicated fixtures for parallel-eligible scenarios may be prepared in parallel once the baseline exists, under Step 7's independence criteria — disjoint actors and data, own-data assertions, no shared mutable state — and Step 7's dispatch rule; baseline setup, artifact pre-state, and `user`-driver preparation stay serial. Inspect existing local data and reuse a suitable tenant, account, and records — except scenarios marked parallel-eligible, which get the dedicated fixtures planned in Step 5 rather than records shared with other selected scenarios. Create missing scenario data and relationships through the real UI under the selected driver, existing project seeds/factories, or targeted application or local database commands. Attempt each applicable path until the required state exists; before blocking, account for each path as required below. An empty database or missing records alone is not a blocker. Prepare only what the selected behavior needs; preserve reproduction-critical values without recreating the customer's whole environment.

Use existing tooling and small, one-off commands. Do not create setup scripts, seeders, fixture generators, verification harnesses, or bulk fixture matrices for this QA pass. Reuse compatible records across a journey. Setup supplies prerequisites, never the behavior's expected result; the selected driver executes shipped artifacts as tests in Step 7, not as hidden fixture setup.

For an already-applied artifact, reconstruct a representative pre-state and make the artifact runnable through its real entry point. Create affected records in their original state. If schema or execution tracking prevents a rerun, restore only the affected pre-state using a project-supported rollback or targeted local commands; the selected driver runs any shipped artifact involved. Apply the boundary's target verification and approval rules before restoration; do not reset, clone, or re-provision the database merely to obtain a clean run. Inspect the reconstructed pre-state, execute the artifact, and verify its effects under Step 7. An already-run artifact or already-repaired data alone is not a blocker, and a no-op against repaired data is not proof of the original change.

Request required access or approval before treating its absence as a blocker — approval grants the agent permission to execute the preparation path itself; the user supplies only `user`-driver UI setup or human-only access. Record a scenario `BLOCKED` only when its required state or execution cannot be obtained after each applicable path was attempted or proven unreachable within the safety rules, or required access or approval is unavailable or declined. A path counts as attempted when its real entry point ran; it is inapplicable only when the project lacks the tooling or entry point the path needs, never because it seems unlikely to work; it is unreachable when an identified prerequisite it depends on failed bounded recovery, and the record names that prerequisite and its evidence. Before recording `BLOCKED`, escalate each missing prerequisite to the user once through the interactive question tool, or a plain chat prompt where it is unavailable: state the missing prerequisite, the paths attempted, and the candidate unblock path; offer supplying the access or action, suggesting another unblock path to attempt once, or keeping the dependent scenarios `BLOCKED` and continuing. A supplied access/action or suggested path grants one more bounded attempt; the blocker clears only when the missing prerequisite is verified in place, otherwise it stands with the failed attempt recorded. A declined, explicitly skipped, or unanswered interactive prompt keeps the blocker. A plain chat prompt yields instead: after independent journeys finish, end the turn with the scenario pending and resume on the reply. Record each path attempted, unreachable, or absent, the specific missing capability or approval, the prompt outcome, and the unblock path; continue independent journeys.

Production copies are an option only when a purpose scenario needs historical state that lightweight local preparation cannot reproduce. Follow `database-tools.md`: confirm production source and local destination; copy only needed records and relationships; preserve reproduction-critical values while masking unrelated sensitive data; isolate mail, queues, webhooks, and external integrations before use. Keep secrets out of evidence and version control; write only to local.

**Recovery:** group setup/tool failures by missing prerequisite. Capture the error, diagnose the cause, and make at most one simple local repair-and-retry for that failure across the run; for a failed parallel fixture stream, remove or quarantine its partial records first so other streams are not contaminated. If it fails, attempt each remaining applicable path once — or record it unreachable when it shares the failed prerequisite — before marking dependent scenarios `BLOCKED` with the recovery record and unblock path. Reopen when new evidence or user-supplied access resolves the blocker. Diagnose application failures only enough to record the finding, not to fix the repo or investigate unrelated code. Record setup errors and dependent blockers in the report, reusing shared proof rather than creating separate unindexed logs.

For external dependencies, use an available sandbox or existing controlled local substitute at the external boundary while executing the real application path. Record the substitution and proof limit; a substitute does not prove provider acceptance. If a criterion requires real provider execution and access is unavailable, ask once for the needed action, then record `BLOCKED` if unavailable.

**Done when:** the next selected scenario has the minimum faithful local prerequisites or a recorded blocker. Deferred scenarios need no data preparation.

### 7. Exercise or Guide the Change

Run coherent journeys serially by default. Parallel execution is optional for agent-driven scenarios independent in data and actor — shared infrastructure is not the barrier. One database, server, or browser process qualifies when scenarios use disjoint tenants, records, and fixtures with non-overlapping values on globally unique fields (names, emails, slugs, sequences); assert only on their own data rather than unfiltered global views, counts, or queues; and avoid shared mutable state or writes such as shipped-artifact execution, feature-flag changes, and global configuration updates. Dispatch parallel work only with three or more independent scenarios or the user's explicit request to delegate, and only when a suitable subagent profile exists — otherwise run the journeys serially. Tabs within one browser context share cookies and storage, so each parallel scenario runs in a separate context or profile for its dedicated actor; same-actor context reuse applies within a serial journey. Stay serial when independence is doubtful; parallelism never justifies scenarios or fixture work beyond the selected plan.

With `<test-driver>` = `agent`, perform the selected actions and collect the results. With `<test-driver>` = `user`, follow `user-driven.md`.

The selected driver exercises UI journeys as a regular user through real navigation, forms, and clicks; agent-driven UI uses `browser-automation.md`. Exercise API contracts, workers/jobs, CLI commands, and artifacts through their real entry points. Console shortcuts, API calls, and DB writes do not replace the main user-facing journey.

For each selected shipped artifact, inspect the pre-state, have the selected driver run the exact command through project tooling in dependency order, then inspect schema and affected rows. Preserve existing rows where required, verify intended changes, and capture any claimed idempotency rerun. Reuse that execution for its purpose and artifact assertions; command success alone does not prove data correctness.

Prove each required persistence or data-integrity outcome with the minimum sufficient evidence. Reuse the journey or an executed existing test when it proves that outcome; a success message or optimistic UI alone does not prove persistence. Query (`database-tools.md`) only when that evidence is insufficient, selecting the relevant records and fields rather than auditing every write or dumping tables. Record the finding and reuse its proof; UI-only assertions need no query. Keep the selected shipped-artifact pre/post checks above. An asserted persisted effect that is wrong fails even if the UI looks right. For repeats, reuse valid existing state and prepare only what the repeat needs within safety and approval rules; no automatic database rebuild.

Use existing focused tests to answer in-scope questions the QA journeys have not proved; select checks by the unanswered risk, not by every touched file. An executed integration test can prove the backend assertions and real entry points it exercises; unit tests prove their narrower calculations. Reuse this evidence for covered critical cases rather than replaying their matrix manually. Neither proves unexercised browser behavior or an unexecuted shipped artifact. Keep the main QA journey and the runtime evidence appropriate to its entry point.

Capture and organize proof checkpoints under [reporting.md](reporting.md), updating the report as execution proceeds. Reuse one artifact for every assertion or scenario it proves rather than repeating execution, screenshots, or queries for the same observed state.

Record `<results>` by ID: steps/command, expected versus observed behavior, evidence paths, and status; user-driven actions include the user's report. An application error reached through the real scenario is `FAILED`; a setup/tool error preventing it follows Step 6. Label a failure pre-existing only with evidence; otherwise leave attribution unconfirmed instead of expanding into an unrelated investigation.

Reconcile the scoped outcomes, plan, and results once: each selected assertion has evidence or a recorded blocker/defer reason, required capture gaps are explicit, each deferred ID has a reason, and planned count = `PASSED` + `FAILED` + `BLOCKED` + `DEFERRED`. Apply reporting.md's artifact/link integrity checks; fill gaps within the selected scope, keep deferred work deferred and unchanged blockers blocked, and stop when this gate passes.

### 8. Report Findings

Finalize the local HTML report under [reporting.md](reporting.md); never post findings to the PR.

- **Verdict** — name the driver. `FAILED` if an evidenced executed scenario failed; otherwise `INCOMPLETE` if no purpose journey executed, a blocker remains, a defining ticket is missing, a required capture has a proof gap, or mixed revisions prevent a clean tested-revision claim; otherwise `PASSED` for the exercised scope. A report delivery blocker prevents an unqualified pass. Include passed, failed, blocked, and deferred counts.
- **Report** — give the absolute `index.html` location. Keep scenario details, expected versus observed behavior, evidence, failures, and test boundaries in the report rather than repeating its table in chat.
- **Actionable findings** — summarize concrete failures, blockers/unblock paths, missing requirements or defining tickets, premise drift, verdicts on admitted `<review-findings>` (confirmed, rebutted, unverified), and proof gaps that need attention. Cite `file:line` only where the diff is implicated; distinguish confirmed pre-existing failures from unknown attribution. Claim only what the evidence proves, not exhaustive application coverage.

## Notes

Verifies, never fixes. Leave application source/tests and repository history as found: no code or test additions, setup scripts, stray commits, or PR updates. Retain only the authorized ignored report package and any explicitly approved narrow local exclusion; fixes require a separate request.
