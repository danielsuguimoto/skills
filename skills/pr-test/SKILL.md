### 0. Select the Test Driver

Use the user's explicit driver choice from this session; otherwise default to `agent`. Record `<test-driver>`: `user` performs test actions with agent guidance and verification; `agent` performs and verifies them, requesting human-only access or actions when needed. The user can change drivers. For `user`, read [user-driven testing](user-driven.md). Both drivers follow the same scope, plan, preparation, and proof rules.

## Required `<project-root>/docs` reads

Shell-read before testing the PR (reuse session reads): `<project-root>/docs/git-hosts.md`; `<project-root>/docs/testing.md` for project-specific testing requirements · `<project-root>/docs/issue-trackers.md` for linked requirements · `<project-root>/docs/database-tools.md` when provisioning or verifying data · `<project-root>/docs/code-navigation.md` for behavioral-surface analysis, entry-point location, or concrete failure diagnosis · `<project-root>/docs/browser-automation.md` for agent-driven UI execution. If a spec is missing, report the gap and use a documented fallback.

Apply `testing.md` to planning, setup, execution, and evidence: startup, test data, actors, browser/environment constraints, external-service substitutes, and supporting checks. It cannot widen `<behavioral-surface>`, waive browser journeys, or replace safety approvals.

Act as a human QA engineer. The tested code defines `<behavioral-surface>`; PR text, tickets, and review feedback supply intent, expected outcomes, and risk signals. When those sources conflict with the code, the code decides what belongs in scope while requirements decide whether that behavior is correct. Choose coverage proportionate to the change's behavior, impact, complexity, and risks: some changes need more paths than others. Prove the main changed journeys and meaningful regressions through realistic use; touched files and methods are not a coverage checklist.

**Concise execution:** Work quietly; omit phase announcements, routine progress, plan recaps, and tool-output transcripts. Send only required questions, approvals, blockers, user-driver guidance, and the final handoff. Batch independent reads and reuse setup, journeys, and evidence where they prove the required outcomes; keep tool output to the relevant facts. Never skip safety, required checks, or proof for brevity.

**Local test authorization:** An explicit PR test request covers the reversible local writes needed for the selected scenarios, supporting checks, and their prerequisites and reruns. This includes fixture inserts and updates, real UI/API/job writes, baseline migrations and seeds, and the intended reversible local effects of PR-shipped migrations, seeders, operations, and scripts. Use the selected driver. Once the target and effects are verified, execute in-scope writes without asking again per step, command, record, or tool. Carry the same authorization into setup, execution, and documented fallbacks.

**Safety boundary:** Before writing, inspect effects and verify the effective database or service target from configuration and connection details for the actual runner (app, worker, CLI, or test runner). Reuse that verification until the target or configuration changes. Keep production read-only and isolate local tests from real recipients, shared queues, webhooks, and live integrations. If the target is uncertain, stop and ask. Describe and obtain specific approval before any irreversible destructive action or real-world side effect, including in PR-shipped artifacts, and before overwriting or deleting existing local data outside the intended reversible changes. Run against the existing local database; no reset or rebuild for convenience. Honor project safety rules and tool-enforced permissions. Leave PR threads, application source/tests, and history untouched. Local file writes are limited to the report package and an explicitly approved narrow local exclusion; follow [reporting.md](reporting.md) for storage and replacement rules.

**Completion gate:** every planned scenario has a result. `PASSED` means execution met its assertions; `FAILED` means it contradicted an assertion; `BLOCKED` means a prerequisite was not prepared within Step 6's bounded attempts or a required action or decision was unavailable/declined, with attempts, known untried alternatives, and an unblock path recorded; `DEFERRED` means the user approved deferring that scenario, with a reason. Missing evidence never means `PASSED` or `FAILED`.

**Deferral gate:** Before marking any scenario `DEFERRED`, explain why, what remains unverified, and the verdict impact; suggest how to exercise or unblock it, or ask for the help needed. Ask the user whether to defer or continue, grouping candidates when useful but obtaining a decision for each. An explicit user instruction to defer a named scenario counts as approval. Continue or no deferral approval → exercise the scenario under Step 6 when within the user's scope; obtain explicit permission before testing an excluded scenario. Without that permission, leave it unexercised and `BLOCKED` until the user approves deferral or execution. When the user ends the session or a required action is unavailable, preserve approved deferrals and observed failures; mark remaining unperformed scenarios `BLOCKED`. Silence or stopping is not deferral approval. Apply this gate to both drivers and at every phase.

### 1. Interpret Arguments

Explicit PR number/URL → `<pr-ref>`; focus areas or constraints → `<additional-context>`. Without an explicit reference, use the unambiguous PR targeted by the session's current work; ambiguous → ask. No session target → use the current branch's open PR (`git-hosts.md`) when unambiguous; otherwise ask.

### 2. Load PR Context

Read the PR and diff (`git-hosts.md`). Extract `<pr-purpose>` as the original reason the PR exists, `<pr-branch>`, `<base-branch>`, `<pr-number>`, `<pr-url>`, and the tickets that define its requirements as `<ticket-refs>`. Distinguish those tickets from historical or incidental references. Unloadable PR → STOP.

Load reviewer feedback through `git-hosts.md`: review threads with resolution state, non-empty review bodies, and flat comments, automated reviewers included. Extract `<review-findings>` — concrete claims, questions, or claimed fixes about observable behavior, with source and state; a finding whose premise no longer exists is `<premise-drift>`. Style, naming, and process remarks are not findings. Inspect commit history or a claimed fixing commit only when needed to identify affected behavior or test scope. Unloadable feedback or needed history → record the gap and continue.

Use the PR diff to locate a provisional `<behavioral-surface>`: each distinct observable behavior whose outcome, input conditions, contract, or data effects the diff appears to change. Include review-driven changes outside `<pr-purpose>` without requiring per-hunk attribution. Identify `<data-artifacts>` — shipped migrations, seeders, operations, and scripts — and risks directly caused by the change. Step 5 expands the surface to the user journeys and neighboring workflows needed to test it.

### 3. Load Linked Context

Load each `<ticket-refs>` entry's body and checklists (`issue-trackers.md`), reusing in-session copies that cover both. Read comments, attachments, or nested links only to resolve a missing requirement or reproduction detail; this scope also governs generic tracker loading instructions. Tool failure → try a configured alternative. If user access or missing content is necessary, ask once; unavailable → record the gap and continue with supported requirements.

Extract `<expected-outcomes>` as the observable behavior the PR promises. Implementation steps, helper methods, test-writing tasks, and validation commands are not separate user journeys; use them to locate behavior or existing checks. Record `<client-cases>` when the source contains a customer report, keeping the reported steps and data conditions that matter to the failure. Historical context does not expand `<pr-purpose>`; review-driven changes enter scope through `<behavioral-surface>` instead.

Start a compact `<coverage-map>` from the provisional `<behavioral-surface>`, these outcomes, client cases, and behavioral review findings to candidate assertions for the planned journeys or focused checks. Flag missing implementation. An outcome whose premise no longer exists → `<premise-drift>`; explain it in the report rather than inventing a scenario for it.

**Done when:** every defining ticket is loaded or has a recorded gap; every provisional `<behavioral-surface>` entry, observable promised outcome, reported customer case, and behavioral review finding from loaded sources is recorded; shipped artifacts and identified risks are listed; the provisional coverage map records any missing implementation and premise drift.

### 4. Align Local Branch

Record `<previous-branch>`. Uncommitted changes → STOP, ask the user to stash/commit. Fetch the PR head and record its commit → `<pr-head-commit>`. Check out `<pr-branch>` — `git switch <pr-branch>` when it exists and tracks the head repository's `refs/heads/<pr-branch>`; any other same-named branch → `git checkout --detach <pr-head-commit>`, never modify it; only when no same-named branch exists → through project tooling (`git-hosts.md`, fast-forward-only checkouts fail on divergence); failure → STOP. Behind `<pr-head-commit>` → sync it yourself per `git-hosts.md`: fast-forward to `<pr-head-commit>` — behind alone never blocks. Ahead or diverged → `git checkout --detach <pr-head-commit>` — the branch ref and its local commits stay untouched; testing never aligns by pushing or rewriting them. Verify HEAD == `<pr-head-commit>` before the initial run — initial evidence against a stale head is invalid. Set initial `<tested-state>` = `T01` for `<pr-head-commit>` and record `<tested-checkout>` as the tested branch or detached commit; the PR head is a baseline, not a continuing validity gate. Step 9 adds tested-state entries for user-directed fixes. Restore `<previous-branch>` only after Step 9 is complete or declined. If `<previous-branch>` is the tested branch, leave user-directed fix changes in place; if it differs and uncommitted fix changes exist, ask whether to stash them or keep the tested checkout before switching; when they are stashed, record the stable stash commit SHA and modified-file summary as `<preserved-fix-state>`; if fix commits exist on a detached checkout, ask whether to keep that checkout or preserve them on a clearly named local branch before switching; never discard them. Before switching, refresh `<tested-checkout>` to the current branch or detached commit. Report where preserved fix changes live.

### 5. Build the Test Plan

Confirm `<behavioral-surface>` against the checked-out tested code before planning: keep, split, merge, or discard provisional entries according to actual behavior. Map each distinct normal entry path, downstream step, and meaningful neighboring workflow sharing a route, permission, job, or data boundary; include unchanged steps users need. Add these journeys and shared-boundary risks to the surface, not just behavior in the diff. Limit navigation to the paths needed to establish this map. Finish `<coverage-map>` from the confirmed surface. If code needed for this confirmation is unavailable, record the gap and treat the affected scope as unverified rather than substituting PR text or ticket scope.

Read [reporting.md](reporting.md) and check destination safety before inspecting any previous report. Reuse useful scenarios that fit the current PR and balanced scope; check the PR for new scenarios. Rerun selected scenarios and collect fresh evidence; previous results do not prove the current run.

Build `<test-plan>` around natural user journeys. A journey may span pages, actors, and lifecycle steps. Map each distinct normal entry path and its needed downstream steps to required coverage; exercise each path or record why it was not exercised. Start main journeys at the normal entry, not a direct URL or other shortcut to a downstream state; use shortcuts only to isolate or supplement evidence. Each selected journey exercises the affected flow end to end: entry, affected behavior, and subsequent steps; a rejected path ends at the rejection with relevant downstream effects verified absent. Select pass-through and guarded paths when requirements or risk justify them, not by a fixed branch rule. Add scenarios for distinct behavior, promised outcomes, behavioral review findings, or risks that selected evidence does not cover. Combine related assertions in one journey.

- **Purpose** — exercise the PR's promised behavior, including the reported customer failure where applicable. Reuse that execution for the requirements it proves.
- **Regression** — map each distinct `<behavioral-surface>` entry outside the purpose that can affect a user-facing feature, API contract, worker/job, CLI command, or artifact to a selected journey or explicit deferred entry, prioritizing review-driven changes and shared-boundary effects. Exercise meaningful neighboring workflows through their normal entry points; fold related assertions into the nearest journey sharing that entry point. Keep internal refactors with no observable behavior out of the scenario ledger.
- **Data-artifact** — execute every `<data-artifacts>` entry against representative populated local data and verify its schema/row effects. Fold this into a purpose or regression scenario when the same execution proves both; otherwise add a dedicated artifact scenario. Re-run only where idempotency is claimed.
- **Edge** — select cases justified by requirements or the impact, likelihood, and complexity of a failure tied to a `<behavioral-surface>` entry. State the concrete risk. Use relevant variations rather than enumerating permutations of roles, tenants, dates, flags, and legacy states.
- **Reviewer finding** — admit a `<review-findings>` entry that claims, questions, or claims to fix distinct observable behavior or regression risk a selected execution does not already prove. Verify the claim against the tested head; a confirmed defect fails like any other. Fold the check into the journey sharing its entry point rather than adding a standalone scenario. Findings without observable behavior need no scenario.

Choose the number and depth of paths by the change's requirements and risk, with no fixed minimum or maximum. Include the main changed journeys, meaningful review-driven regressions, required artifacts, and justified edges; avoid duplicate evidence. A user-supplied focus can narrow execution when recorded as a boundary; apply the deferral gate to excluded important regressions.

Prioritize by user impact and regression risk rather than source. Keep each selected dependency chain complete: prerequisites run before dependent assertions and count within a journey when they are part of the same scenario. Propose deferring a low-priority chain whole when its setup cost outweighs its behavioral risk; apply the deferral gate before excluding it. Apply this judgment before detailed setup or data provisioning.

Give each scenario an ID, source outcome or `<behavioral-surface>` entry, entry point, prerequisites, and observable assertions; add the risk for an edge, regression, or reviewer-finding scenario. Map each required entry path to a scenario ID and identify it in the source so unexercised paths remain visible even when deferred. Match fixtures and inputs to each assertion: use representative source data and compare with the expected result when asserting content or downstream effects. Delivery or preservation alone does not prove content correctness or other unobserved effects. Verify distinct in-scope effects separately. Map each required in-scope `testing.md` supporting check to the assertion or risk it supports, and give it a stable `Cnn` result ID, command or entry point, and prerequisites. These checks supplement the mapped evidence and do not add scenario rows. Deferred IDs need only their source and reason. Out-of-scope permutations need no scenario rows; summarize that boundary once. Every non-drifted `<behavioral-surface>` entry, promised outcome, and behavioral `<review-findings>` entry maps to a selected assertion or a deferred ID; findings without observable behavior need no rows, and implementation and automated-test checklists do not inflate this ledger.

**Done when:** the plan accounts for `<behavioral-surface>`, requirements, review-driven regressions, required artifacts, and relevant risks through selected or explicitly deferred work; each selected journey covers its affected flow with executable dependencies; and scenarios do not repeat evidence already supplied. Resolve and authorize the report destination under reporting.md before Step 6; unresolved storage safety pauses testing.

### 6. Prepare Minimal Local Data

Prepare the shared baseline first, then the main journey's data, and later prerequisites when needed. Start only required processes; inspect the local database and apply baseline migrations or seeders only when needed for the selected scenarios or required by `testing.md`. Exclude selected `<data-artifacts>` from baseline setup: prepare their pre-state, then execute them under the selected driver through Step 7 before dependent journeys. Reuse suitable local tenants, accounts, and records. Create missing data through the real UI under the selected driver, existing seeds/factories, or targeted application or local database commands. An empty database or missing records alone is not a blocker. Prepare only what the selected behavior needs; preserve reproduction-critical values.

Use existing tooling and small, one-off commands. Do not create setup scripts, seeders, fixture generators, verification harnesses, or bulk fixture matrices for this QA pass. Reuse compatible records across a journey. Setup supplies prerequisites, never the behavior's expected result; the selected driver executes shipped artifacts as tests in Step 7, not as hidden fixture setup.

For an already-applied artifact, reconstruct a representative pre-state and make the artifact runnable through its real entry point. Create affected records in their original state. If schema or execution tracking prevents a rerun, restore only the affected pre-state using a project-supported rollback or targeted local commands; the selected driver runs any shipped artifact involved. Apply the boundary's target verification and approval rules before restoration; do not reset, clone, or re-provision the database merely to obtain a clean run. Inspect the reconstructed pre-state, execute the artifact, and verify its effects under Step 7. An already-run artifact or already-repaired data alone is not a blocker, and a no-op against repaired data is not proof of the original change.

Use the local test authorization for fixtures and other covered setup; do not request consent again. Ask only for unavailable access, human-only actions, or an approval the safety boundary requires. Group known access needs in one request without bundling or waiving specific approval for irreversible actions. Once access or approval is granted, execute covered preparation yourself except for actions assigned to the user driver. Try the best supported preparation path and, if it fails, one plausible fallback when available. A path counts as attempted when its real entry point ran. If the prerequisite remains unavailable, record the scenario or required check `BLOCKED`:

- Before recording `BLOCKED`, escalate each missing prerequisite to the user once — through the interactive question tool, or a plain chat prompt where it is unavailable: state the missing prerequisite, the paths attempted, and the candidate unblock path.
- A supplied access, action, or suggested path grants one more bounded attempt; the blocker clears only when the missing prerequisite is verified in place.
- A declined or unanswered prompt keeps the blocker; a plain chat prompt yields after independent journeys finish and resumes on the reply.
- Record the failure, attempted paths, known untried alternatives, and unblock path; continue independent journeys. `BLOCKED` means the prerequisite was not obtained, not that every possible path is impossible.

Production copies are an option only when a purpose scenario needs historical state that lightweight local preparation cannot reproduce. Follow `database-tools.md`: confirm production source and local destination; copy only needed records and relationships; preserve reproduction-critical values while masking unrelated sensitive data; isolate mail, queues, webhooks, and external integrations before use. Keep secrets out of evidence and version control; write only to local.

**Recovery:** group setup/tool failures by missing prerequisite. Capture the error, diagnose the cause, and make at most one simple local repair-and-retry per failure. If it fails, use the bounded fallback and blocker process above. Reopen when new evidence or user-supplied access resolves the blocker. Diagnose application failures only enough to record the finding, not to fix the repo or investigate unrelated code. Record setup errors and dependent blockers in the report.

For external dependencies, use an available sandbox or existing controlled local substitute at the external boundary while executing the real application path. Record the substitution and proof limit; a substitute does not prove provider acceptance. If a criterion requires real provider execution and access is unavailable, ask once for the needed action, then record `BLOCKED` if unavailable.

**Done when:** the next selected scenario has the minimum faithful local prerequisites or a recorded blocker. Deferred scenarios need no data preparation.

### 7. Exercise or Guide the Change

Run coherent journeys serially by default. Parallel execution is agent-driven only and requires a suitable subagent profile; decide it before running any scenario — when three or more selected scenarios are independent in actor and data, or when the user requests delegation. Independent means disjoint tenants, records, and fixtures with non-overlapping values on globally unique fields (names, emails, slugs, sequences); assertions only on own data rather than unfiltered global views, counts, or queues; and no shared mutable writes such as shipped-artifact execution, feature-flag changes, or global configuration updates. Shared infrastructure is not the barrier — one database, server, or browser process qualifies. The parent prepares dedicated fixtures before dispatch when selected scenarios share records; parallel workers do not write shared fixtures, and a failed fixture stream's partial records are removed or quarantined before other streams proceed. Tabs within one browser context share cookies and storage, so each parallel scenario runs in a separate context or profile for its dedicated actor. Stay serial when independence is doubtful; parallelism never justifies scenarios or fixture work beyond the selected plan.

With `<test-driver>` = `agent`, perform the selected actions and collect the results. With `<test-driver>` = `user`, follow `user-driven.md`.

The selected driver exercises UI journeys as a regular user through real navigation, forms, and clicks; agent-driven UI uses `browser-automation.md`. Run each selected browser journey end to end in a browser against `<tested-state>`. Non-browser automated tests (unit, integration, API, or otherwise) only supplement it; overlapping names or coverage do not replace it. Count an automated browser E2E test only when the selected driver launches it and it runs the same journey, inputs, and assertions against `<tested-state>` with inspectable evidence; otherwise the selected driver performs the journey. Exercise API contracts, workers/jobs, CLI commands, and artifacts through their real entry points. Console shortcuts, API calls, and DB writes do not replace the main user-facing journey.

Use the existing local test authorization for covered effects; stop before any effect that requires specific approval and lacks it.

For each selected shipped artifact, inspect the pre-state, have the selected driver run the exact command through project tooling in dependency order, then inspect schema and affected rows. Preserve existing rows where required, verify intended changes, and capture any claimed idempotency rerun. Reuse that execution for its purpose and artifact assertions; command success alone does not prove data correctness.

Prove each required persistence or data-integrity outcome with the minimum sufficient evidence. Reuse the journey or an executed existing test when it proves that outcome; a success message or optimistic UI alone does not prove persistence. Query (`database-tools.md`) only when that evidence is insufficient, selecting the relevant records and fields rather than auditing every write or dumping tables. Record the finding and reuse its proof; UI-only assertions need no query. Keep the selected shipped-artifact pre/post checks above. An asserted persisted effect that is wrong fails even if the UI looks right. For repeats, reuse valid existing state and prepare only what the repeat needs within safety and approval rules; no automatic database rebuild.

Use discretionary existing focused tests only for in-scope risks the required end-to-end journeys leave open; select checks by unanswered risk, not by touched files. An executed integration test can prove the backend assertions and real entry points it exercises; unit tests prove their narrower calculations. Reuse this evidence for covered critical cases rather than replaying their matrix manually. Neither proves unexercised browser behavior or an unexecuted shipped artifact. Keep the main QA journey and the runtime evidence appropriate to its entry point. Run each planned required check through its recorded entry point against `<tested-state>` even when it overlaps browser coverage; it supplements rather than replaces the journey. Record it under its `Cnn` ID; its outcome contributes to the mapped assertion or scenario status.

Capture and organize proof under [reporting.md](reporting.md), recording observations as execution proceeds. Reuse one artifact for every assertion or scenario it proves rather than repeating execution, screenshots, or queries for the same observed state.

Record `<results>` by ID: tested-state ID, steps/command, expected versus observed behavior, evidence paths, and status; user-driven actions include the user's report. Record each required path's outcome and evidence or reason it was unexercised, even when paths share a scenario. An unexpected application error in a selected scenario or on a required path is `FAILED` even if the PR did not introduce it. Record a required-path failure in its mapped scenario and mark that scenario `FAILED` even if it was deferred; retain the original observation and deferral reason. A setup/tool error preventing execution follows Step 6. Record direct checks separately from the normal-path outcome. Label a failure pre-existing only with evidence; otherwise leave attribution unconfirmed instead of expanding into an unrelated investigation.

### 8. Report Findings

Write the local HTML report under [reporting.md](reporting.md); never post findings to the PR. Keep its required fields brief: use short factual phrases, combine related actions and assertions, and link shared evidence instead of repeating observations or output. Omit narrative, redundant explanations, and routine successful-step commentary. Preserve provenance, results, proof, and gaps.

- **Verdict** — name the driver. `FAILED` if an evidenced executed scenario, required path, or required in-scope `testing.md` check failed; otherwise `INCOMPLETE` if a required path was not exercised, a required assertion lacks proof, no main `<behavioral-surface>` journey executed, a blocker remains, a defining ticket is missing, a required capture has a proof gap, or a required in-scope `testing.md` check is missing or unrun; otherwise `PASSED` for the exercised scope. A deferred or user-excluded required path remains unexercised. A report delivery blocker prevents an unqualified pass. Base the verdict on the evidence attached to each tested-state entry; record mixed or local working-tree provenance as a boundary. Include scenario passed, failed, blocked, and deferred counts; report supporting-check results separately.
- **Chat** — one compact handoff with the verdict details and absolute `index.html` path. Name what passed, failed, and remains unverified; add short bullets for blockers/unblock paths, missing requirements or defining tickets, premise drift, and proof gaps requiring attention. Keep scenario details, evidence, and verdicts on admitted `<review-findings>` (confirmed, rebutted, unverified) in the report. Cite `file:line` only where the diff is implicated; distinguish confirmed pre-existing failures from unknown attribution. On a delivery blocker, state that no report was published, give the absolute report-package path for captures, and summarize the observed results and proof gaps; never present the unvalidated staged draft as a finished report. Claim only what the evidence proves.

### 9. Continue After Failed or Blocked Results

For `FAILED` or `BLOCKED` scenarios or required checks, ask in one round for **unblock**, **fix**, or **leave as reported**, via the interactive question tool or chat fallback. If the user ends the session, leave remaining results as reported without requesting continuation. Accept volunteered directions. Use multi-select for combined directions where supported; otherwise ask by item when needed. Scope the continuation to named items or items the chosen fix or prerequisite affects; ask once if the scope or path remains unclear. Leaving results as reported requires no rerun.

- **Unblock:** follow the recorded or user-supplied path under Step 6 and its safety and approval rules; verify the prerequisite, and rerun affected blocked items.
- **Fix:** the user's direction authorizes only named, uncommitted source edits; verify an existing fix rather than editing again. Commit or push only on a separate request. Rerun affected failures and blockers whose prerequisites the fix restores.

Before editing or rerunning, verify the intended tested checkout or the user-selected fixed checkout. Re-enter it if the prior branch was restored. For a preserved stash, verify the recorded modified files; if absent, apply `<preserved-fix-state>` without dropping it unless the user selected a different checkout. Stop and ask if you cannot restore the checkout or edits without disturbing user changes.

When tested code changes, record the next state ID (`T02`, `T03`, ...) with the actual tested commit SHA (including a locally committed fix), uncommitted changes, and modified files. Set `<tested-state>` to that ID; retain it when the tested code is unchanged. A local working tree is valid without commit, push, or PR-head update. Restore minimum prerequisites under Step 6, rerun affected journeys end to end under Step 7, including the failed required paths, and required checks through their recorded entry points, then tag fresh evidence with the tested state ID. Keep earlier results and IDs for independent items; clear no result without fresh execution.

Regenerate the report under [reporting.md](reporting.md) with fresh results and evidence, even if the verdict stands. Check destination safety. On delivery failure, preserve fresh evidence and disclose the blocker. Report verdict, counts, remaining failures or blockers, and absolute report location.

**Done when:** the continuation is executed or declined; any rerun is reconciled into a regenerated report or its delivery blocker disclosed; the verdict, counts, and report location are reported; and `<previous-branch>` is restored or its restoration decision recorded while preserving user-directed fix changes.

## Notes

Verifies, never fixes on its own. During the initial pass, leave application source/tests and repository history as found: no code or test additions, setup scripts, stray commits, or PR updates. Retain only the authorized ignored report package and any explicitly approved narrow local exclusion; fixes require a separate request. A Step 9 fix direction is that separate request and authorizes only the directed uncommitted source changes; all other boundaries remain.
