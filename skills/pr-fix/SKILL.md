description: "Fix PR review feedback, respond to inline threads, review bodies, or flat comments, and resolve addressed threads."

## Required `<project-root>/docs` reads

Shell-read before fixing PR review feedback (reuse session reads): `<project-root>/docs/git-hosts.md`. If a spec is missing, report the gap and use a documented fallback.

### 1. Interpret Arguments
`auto` → `<execution-mode>` = `auto`; extra guidance → `<additional-context>`; otherwise → `review`. Resolve `<pr-ref>` from the explicit PR number/URL, else the unambiguous PR targeted by the session's current work. Missing or ambiguous → ask; never pick an unrelated PR. Load current PR state even when its reference came from the session.

### 2. Load PR Context
Resolve the repo root. Record `<repo-path>`, `<pr-branch>`, `<base-branch>`, `<pr-number>`, `<pr-url>`, and `<current-branch>`. Load PR metadata, unresolved review threads, reviews, and flat comments via `git-hosts.md`; batch independent reads. Filter threads server-side when supported; otherwise use the documented review-thread fallback and filter by resolution state. Use REST review-comment IDs only to match replies, never as the unresolved-thread list. Keep first-comment IDs and thread node IDs for replies and resolution.

Collect nonempty review bodies and flat comments even when no threads exist. Keep author, body, and ID; keep the latest restatement of each reviewer's finding. For findings also covered by a thread, carry the latest restatement into that thread's analysis record and keep the thread as the reply location; retain distinct flat findings as `<flat-feedback>`. Include bot findings; skip own-agent items and CI, coverage, or deployment notices. Read relevant attachments. If no feedback remains, report no changes and stop before checkout.

Anchor `<pr-intent>` — why the PR exists: title, body, commit messages, and a ticket brief (see Ticket Brief) for all issue/card references in the body, commits, or branch name, scoped to intended behavior and constraints. For each scope-relevant target PR decision reference returned by the brief, reuse loaded feedback or retrieve only that decision and the context needed to establish its status via the git host (`git-hosts.md`); unavailable or ambiguous → note the gap. No usable brief → fall back to PR title/body plus any verified decision; note the gap. Feedback identifies claims to investigate; intent arbitrates scope.

### 3. Align Local Branch
`<pr-branch>` unavailable → STOP. Inspect the worktree and index; uncommitted or untracked changes → STOP and ask the user to preserve them before continuing. Fetch the PR head and record its commit → `<pr-head-commit>`. Check out `<pr-branch>` — `git switch <pr-branch>` when it exists and tracks the head repository's `refs/heads/<pr-branch>`; any other same-named branch is a collision → `git switch -c` a distinct branch at `<pr-head-commit>`, never modify it; only when no same-named branch exists → git host checkout PR or `gh pr checkout <pr-number>` (checkout tools fast-forward only and fail on a diverged branch) → `<active-branch>`; fails → STOP; match a Git remote to the head repository — fork checkouts may add it → `<head-remote>`. Behind `<pr-head-commit>` → sync it yourself per `git-hosts.md`: fast-forward to `<pr-head-commit>` — behind alone never blocks. Ahead (unpushed local commits on top of `<pr-head-commit>`) → continue; the flow's push publishes them — flag them in the report. Diverged → `git rebase <pr-head-commit>` only when the replay range is linear — merge commits can carry edits a clean replay silently drops → a merge in the range → STOP; a clean replay — already-upstream commits drop on their own — leaves the branch containing `<pr-head-commit>` → continue, flag the replayed commits in the report; conflict → `git rebase --abort`, STOP and report. No code edits until HEAD is on `<active-branch>` and `<pr-head-commit>` is an ancestor of it — `<pr-branch>` stays the remote destination, not a required local name. Never skip checkout — `<pr-ref>` is authoritative.

### 4. Load Changes
Git host PR diff. Fallback: `gh pr diff <pr-number>` or `git diff <base-branch>...<active-branch>` → `<changes>`.

### 5. Analyze Feedback
1. Review unresolved threads; check review states (`CHANGES_REQUESTED`, `APPROVED`, etc.). Every `<flat-feedback>` item is reviewer feedback, not metadata — a prose ask needs no line anchor or code suggestion to warrant investigation; flat items alone are a complete work set.
2. Use `<changes>` to understand the diff. Prioritize critical issues (bugs, security, broken contracts).
3. Previously addressed: threads with a "Fixed..."/"Done..." reply plus a commit newer than the finding implementing it, or an evidence-backed reply that fully answers the concern; flat items addressed by a commit newer than the item or confirmed fixed in a later reviewer body — verify fixes via commit diff. Skip implementation and duplicate replies; retain addressed inline threads for resolution. In doubt → ask.
4. For every finding, including flat feedback, independently check the claimed problem and proposed fix. Treat reviewer comments as hypotheses, not facts: trace the relevant current code and behavior; for claims about persisted schema or data, inspect the live database read-only via `<project-root>/docs/database-tools.md` when available. Code establishes behavior; the live database establishes persisted schema and state. For migration claims, verify the database's applied migrations or revision; an older schema does not establish the result of an unapplied migration. Inspect the migration code for proposed changes, and report any missing evidence before claiming the resulting state. Compare the evidence with `<changes>` and `<pr-intent>`; a reviewer may lack context, and a valid concern does not make its proposed fix correct. Classify the concern separately from the remedy: disproven concern → `not-fixing` with evidence; supported concern → validate the proposed fix or, if unsuitable or absent, an alternative. Record the validated remedy as `<selected-fix>`, separate from the original `<suggestion>`; reject a harmful remedy without discarding a supported concern. No viable remedy → `not-fixing` with evidence; insufficient evidence → report the gap and ask before applying. Inspect other relevant live state read-only via the applicable spec, such as `<project-root>/docs/observability-tools.md` or `<project-root>/docs/bug-trackers.md`. Record `<comment-id>`, `<file>`, `<lines>`, `<category>`, `<suggestion>`, `<reviewer-body>`, `<current-heading>`; flat items omit `<file>`/`<lines>` — the item's prose request is its `<suggestion>`. `noise`/`question` items → `not-fixing` with reasons (`<reviewer-body>` recorded there only, for Step 12).
5. Scope creep — assess each `<selected-fix>` against the PR and related ticket scope, including its likely change footprint. Sound but outside `<pr-intent>`, ambiguous, or likely to expand the PR substantially (pre-existing bug, adjacent refactor, broader coverage, "while you're here" work) → STOP before implementing it and ask the user to confirm the scope expansion, stating the reason and expected footprint. This gate also applies in `auto` mode. Explicit approval → amend `<pr-intent>` with the approved expansion for planning; otherwise add it to `not-fixing` with the reason. A supported concern with a validated, in-scope or approved `<selected-fix>` → actionable.

### 6. Plan Implementation
Fast path: every actionable item has passed Step 5's evidence check and has a straightforward `<selected-fix>` with no conflicts → `<implementation-plan>` = `trivial` — on this path partition items into `<fix-groups>` (shared file lands in one group) and mark `parallel-eligible` per the criteria below before skipping to Step 7 when dispatch is viable: three or more groups or the user's explicit request. Skip fast path when any item is ambiguous, has cross-item dependencies, or needs judgment. Otherwise: ordered fix list (`critical` → `important` → `style`, then file, then line); `noise`/`current-heading: yes`, invalid concerns (misreading), and scope expansions declined in Step 5 → `not-fixing` with reason (reply why in Step 12). An invalid `<selected-fix>` (would break behavior or contradict `<pr-intent>`) → return to Step 5 to reassess alternatives. Map cross-item dependencies as sequential thinking → `<dependencies>`; partition actionable items into `<fix-groups>` and mark a group `parallel-eligible` when its files are disjoint from the other groups, it has no cross-group dependencies, and it runs no commands writing shared mutable state such as lockfiles or build caches.

### 7. Implement Fixes
Critical first, existing patterns, `<active-branch>`, focused minimal changes — implement the validated fix for each actionable item, with adjacent refactor, hardening, or cleanup only if approved in Step 5. An unexpected scope expansion emerges → stop before expanding and return to Step 5. `parallel-eligible` `<fix-groups>` may be implemented in parallel — dispatch one subagent per group, each editing only its assigned files — only with three or more groups or the user's explicit request to delegate, and only when a suitable subagent profile exists; doubtful independence stays serial. Collect each group's changed files into `<fix-files>`, verifying they stayed within its boundaries; a failed group's changes are discarded or reset before validating or committing — never mix successful and failed group edits; its items are retried serially in this session, and items still unfixed are surfaced at the approval gate, never counted as fixed. Validation, commit, and thread replies stay serial in this session. → `<changes-count>` and `<fix-files>`.

### 8. Validate Changes
Run checks appropriate to the changed behavior and risk, batching shared lint and tests once after the fixes. For a non-behavioral change, use a proportional check rather than running unrelated tests. Confirm fixes and proposed or existing evidence-backed replies address their feedback. For code-dependent replies or resolutions, verify evidence against `<pr-head-commit>` when no push is planned, or the exact tree to be pushed; record any ahead commits required to publish it → `<validation-results>`, `<validation-passing>` (`yes`/`no`).

### 9. Approve the Batch (`review` mode)
Stop on failed validation. Identify threads that will be fully addressed by a verified fix or a proposed or existing evidence-backed reply, including threads needing no code changes; list those that will meet Step 13's criteria after any proposed push and replies succeed. If no fixes, replies, or resolutions are planned, report and stop. In `auto` mode, the explicit `auto` argument authorizes the batch without this question, including any scope expansion approved in Step 5. Otherwise show the PR, one line per fix, file count, validation, any existing commits the push would publish, and feedback items to reply to and threads to resolve. Show comment-only and resolution-only work even when there are no code changes.

Ask once: "Approve this batch for <pr-url>: commit the listed fixes (if any), push the listed fixes and existing commits (if any), post the listed replies, and resolve the listed fully addressed threads?" Offer `Go Ahead` and `Needs Review`. Only `Go Ahead` approves. An unanswered or declined gate stops publication.

`Go Ahead` authorizes Steps 11-13 for this PR and listed batch. Execute them in order without asking again for individual commits, pushes, replies, or resolutions. Keep the same approval when switching to a documented fallback. Honor tool-enforced permissions and higher-priority safety gates; never bypass them. If the target or batch changes materially after approval, return to this gate in `review` mode, even if the run started in `auto`.

### 10. Apply Review Feedback
`Needs Review` → refine within scope, regroup if the affected files changed, rerun Steps 7–9. Publish nothing until approved.

### 11. Commit and Push (after `approved` or `auto`)
No fixes to commit and no approved ahead commits needed for evidence → skip to Step 12. If the head moved, retry only for the same approved batch; a material change returns to Step 9 before publication.
Inspect the worktree and index again, including changes within `<fix-files>`. Unexpected changes → STOP and preserve them. When fixes exist, stage and commit only `<fix-files>` with explicit pathspecs. Push fixes or approved ahead commits needed for evidence via `git push <head-remote> <active-branch>:<pr-branch>`. Rejected non-fast-forward — the head moved since `<pr-head-commit>` → re-fetch; `git rebase --onto <new-head> <pr-head-commit>` — replays only commits added on top of the recorded head, so replaced PR commits never return; linear range only → a merge → STOP; clean → revalidate on the rebased tree; retry once only if validation passes and the batch is unchanged, then record `<pr-head-commit>`; conflict → `git rebase --abort`, STOP — never force-push. Never use a generic message like "address review feedback" → `<pushed>` (`yes`/`no`).

### 12. Respond to Threads
Execute the approved replies after a successful push or on the authorized comment-only or resolution-only path. For code-dependent replies, confirm the evidence is present on the published PR head; otherwise leave the thread open and report the blocker. Reply in each relevant thread with the fix or reason for skipping, except where an existing reply already addresses it. Post a flat comment only when needed to address distinct flat feedback or when no threads need replies; quote the item and tag its author. Resolution-only work needs no new reply or flat summary. Do not post a flat summary duplicating thread replies. If a write result is uncertain, check for the reply before retrying.

### 13. Resolve Addressed Threads
Under the same approval, resolve a listed inline thread after its reply succeeds or an existing reply is verified, and its concern is fully addressed by a verified fix or an evidence-backed explanation or answer. Code-dependent evidence must be present on the published PR head. A skipped code change does not prevent resolution. Leave blocked, deferred, partially addressed, reviewer-reopened, or reviewer-decision-pending threads open. Use thread node IDs from Step 2; look up missing IDs by first-comment ID via `git-hosts.md`. Refresh affected thread state before resolution if there is evidence the review changed. Flat feedback has no resolution. Report any reply or resolution that failed or was blocked.

## Ticket Brief

Reuse current session evidence that covers the references, scoped answers, and decision status. Otherwise read inline, or delegate one isolated, read-only inspection when a bounded scan would add distracting context and a cited brief suffices, or the user requests delegation. Give the worker the references, scope, `<project-root>`, these rules, and target PR when known. Worker cannot run → read inline; spec unavailable → report the gap. An evidence blocker returned by a completed lookup is final, not a reason to retry.

Reader: read `<project-root>/docs/issue-trackers.md`. Dedupe by tracker and ID; read title and the body, checklists, or metadata needed for the scope. Read the latest comment page when scope includes behavior or constraints. Read older comments, attachments, and linked tickets only to close a scope gap or settle an unclear decision; this overrides general tracker traversal. For the target PR, return relevant decision references without fetching its feedback. Follow other PR links only for specific evidence the scope needs. Ignore unrelated bundled content; leave tracker state unchanged.

Return cited answers, decision status (confirmed, proposed, or superseded), blockers, and evidence gaps. Cite tickets, comment permalinks, or attachment names and locations; omit raw threads and attachments. Mark answers partial if unseen material could change them. Stop when the scope is supported.

## Output
Report fixes, validation, push status, replies, resolutions, and remaining blockers.
